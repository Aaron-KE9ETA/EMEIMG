EMEIMG Prototype
Created on May 23, 2026

Author:
    Aaron Cocanower KE9ETA

Overview:
    EMEIMG is an experimental vector-image reconstruction protocol intended
    for transmitting simple image drawing instructions through JT65B-sized
    13-character text packets.

Canvas:
    The receiver reconstructs the image on a fixed 720x480 pixel canvas.

    Decimal:
        Width  = 720
        Height = 480

    Base-36:
        Width  = K0
        Height = DC

    Valid visible coordinate range:
        X: 00 through JZ  -> 0 through 719 decimal
        Y: 00 through DB  -> 0 through 479 decimal

General Packet Structure:
    ICSXXXXXXXXXX

    I = instruction index / render order
    C = color code
    S = shape code
    X = shape-specific payload data

    Each packet is exactly 13 characters.

    The instruction index I ranges from 0 to Z in base-36.
    Packets are rendered in ascending instruction index order, regardless of
    receive/load order.

    Exact duplicate packets may be removed before rendering.

    Most numeric fields are encoded in base-36.
    Two-character coordinate fields such as XX or YY are decoded as one
    two-character base-36 number.

Text Packet Note:
    Shape 0 uses the final six payload characters as literal text.
    These characters may include spaces. Do not strip trailing spaces from
    packet strings before parsing; only strip newline characters from file input.

Color Codes:
    0 = Black
    1 = White
    2 = Gray
    3 = Red
    4 = Green
    5 = Blue
    6 = Yellow
    7 = Cyan
    8 = Magenta
    9 = Brown
    A = Tan
    B = Beige
    C = Wheat
    D = Sandybrown
    E = Sienna
    F = Chocolate
    G = Gold
    H = Crimson
    I = Indigo
    J = Hotpink
    K = Orange
    L = Purple
    M = Lime
    N = Aliceblue
    O = Ivory
    P = Lavender
    Q = Mistyrose
    R = Papayawhip
    S = Seashell
    T = Silver
    U = Lightgray
    V = Darkslategray
    W = Dimgray
    X-Z = Reserved / unused

Shape Codes:
    S: Shape Instructions
	0 = 6-character string
	1 = Line
	2 = Rectangle
	3 = Ellipse
	4 = Triangle Outline
	5 = Triangle Fill
	6 = Arrow
	7 = Star
	8 = SemiCircle / Arc
	9 = Yagi Antenna
	A = Dish Antenna
	B = Radio Transceiver
	C = Radio Waves
	D = Moon
	E = DoubleBox
	F-Z = Reserved / unused


Shape Packet Formats:
=====================

0: 6-Character String
---------------------
    IC0XXYY******

    XX,YY = text origin point
    ****** = six literal text characters

    Draws a six-character text string at coordinate XX,YY.
    The text field may contain spaces.


1: Line
-------
    IC1XXYYxxyy**

    XX,YY = first endpoint
    xx,yy = second endpoint
    **    = unused wildcard values

    Draws a line from XX,YY to xx,yy.



2: Rectangle
------------
    IC2XXYYxxyyF*

    XX,YY = first corner
    xx,yy = opposite corner
    F     = fill flag
            0 = outline
            1 = filled
    *     = unused wildcard value

    Draws a rectangle using XX,YY and xx,yy as opposite corners.

3: Ellipse
----------
    IC3XXYYRrSF**

    XX,YY = center point
    R     = vertical radius
    r     = horizontal radius
    S     = scale factor
    F     = fill flag
            0 = outline
            1 = filled
    **    = unused wildcard values

    Draws an ellipse centered at XX,YY.

    Rendered radii:
        vertical radius   = R * S
        horizontal radius = r * S



4: Triangle Outline
-------------------
    IC4XXYYVLDROS

    XX,YY = origin vertex
    V     = downward vector for point 1
    L     = leftward vector for point 1
    D     = downward vector for point 2
    R     = rightward vector for point 2
    O     = orientation
    S     = scale factor

    Draws an outlined triangle.

    The origin vertex is at XX,YY.

    Before rotation and scaling, the other two points are defined relative
    to XX,YY as:

        point 1 = (-L, V)
        point 2 = ( R, D)

    Orientation:
        0 = default
        1 = 90 degrees clockwise
        2 = 180 degrees
        3 = 270 degrees clockwise

    The scale factor is applied to the V, L, D, and R vector values.


5: Triangle Fill
----------------
    IC5XXYYVLDROS

    Same geometry as Shape 6, but the triangle is filled instead of outlined.


6: Arrow
--------
    IC6XXYYOS****

    XX,YY = arrow tip / vertex
    O     = orientation
    S     = scale factor
    ****  = unused wildcard values

    Draws a solid arrowhead at XX,YY, then draws a rectangular tail behind it.

    Orientation:
        0 = points upward
        1 = points right
        2 = points downward
        3 = points left

    The scale factor controls the size of the arrow.


7: Star
-------
    IC7XXYYRS****

    XX,YY = center point
    R     = radius
    S     = scale factor
    ****  = unused wildcard values

    Draws a four-line star centered at XX,YY.

    The star consists of:
        - vertical line
        - horizontal line
        - diagonal NE/SW line
        - diagonal NW/SE line

    Each line intersects at XX,YY.

    Rendered radius:
        R * S

    The full length of each line is approximately:
        2 * R * S


8: SemiCircle / Arc
-------------------
    IC8XXYYRSOODD

    XX,YY = center point
    R     = radius
    S     = scale factor
    OO    = start angle in degrees
    DD    = angular distance in degrees

    Draws an arc centered at XX,YY.

    Rendered radius:
        R * S

    Angle convention:
        0 degrees points directly right.
        Angles increase counterclockwise.
        90 degrees points upward.
        180 degrees points left.
        270 degrees points downward.

    OO and DD are two-character base-36 fields representing decimal degrees.

    Examples:
        DD = 90  -> quarter circle
        DD = 180 -> half circle
        DD = 360 -> full circle


9: Yagi Antenna
---------------
    IC9XXYYOS****

    XX,YY = macro origin point
    O     = orientation
    S     = scale factor
    ****  = unused wildcard values

    Draws a Yagi antenna macro.

    In orientation 0, the main boom is drawn from:

        (XX + 30*S, YY + 0*S)
        to
        (XX + 0*S,  YY + 100*S)

    The Yagi also draws 4 perpendicular antenna elements spaced evenly along
    the boom.

    At scale 1:
        boom reference size = 30x100 pixels
        element length      = 22 pixels total

    Orientation:
        0 = default
        1 = 90 degrees clockwise
        2 = 180 degrees
        3 = 270 degrees clockwise

    The scale factor is applied as an integer multiplier to the default
    geometry.


A: Dish Antenna
---------------
    ICAXXYYOS****

    XX,YY = dish center / origin point
    O     = facing direction
    S     = scale factor
    ****  = unused wildcard values

    Draws a dish antenna macro.

    The dish consists of:
        - a quarter-circle reflector arc
        - two radial support lines from XX,YY to the arc endpoints
        - a filled center hub circle at XX,YY
        - a vertical mast extending down from the midpoint of the arc

    Facing direction:
        0 = dish faces left
        1 = dish faces right

    At scale 1:
        reflector radius = 40 pixels
        hub radius       = 5 pixels
        mast length      = 30 pixels

    The scale factor is applied as an integer multiplier to the default
    geometry.


B: Radio Transceiver
--------------------
    ICBXXYYS*****

    XX,YY = macro origin point
    S     = scale factor
    ***** = unused wildcard values

    Draws a radio transceiver macro.

    The main radio body uses XX,YY as its top-left corner.

    At scale 1:
        body rectangle = 50 pixels wide by 20 pixels tall
        knob radius    = 5 pixels
        screen size    = 20 pixels wide by 10 pixels tall

    The knob is placed near the left side of the radio body and centered
    vertically.

    The screen is drawn inside the radio body.

    The scale factor is applied as an integer multiplier to the default
    geometry.


C: Radio Waves
--------------
    ICCXXYYRSOODD

    XX,YY = center point
    R     = radius of first wave
    S     = scale factor
    OO    = start angle in degrees
    DD    = angular distance in degrees

    Draws 3 concentric arc segments centered at XX,YY.

    Angle convention:
        0 degrees points directly right.
        Angles increase counterclockwise.
        90 degrees points upward.
        180 degrees points left.
        270 degrees points downward.

    The first wave has radius:
        R * S

    Each additional wave is spaced farther out by:
        2 * R * S

    Rendered wave radii:
        R * S
        R * S + 2 * R * S
        R * S + 4 * R * S

    Simplified:
        1 * R * S
        3 * R G* S
        5 * R * S


D: Moon
-------
    ICDXXYYSK****

    XX,YY = center point
    S     = scale factor
    K     = crater color
    ****  = unused wildcard values

    Draws a filled moon centered at XX,YY.

    The moon body uses the packet color C.

    Rendered moon radius:
        36 * S

    The moon also draws 10 outlined crater circles using color K.

    Crater positions are fixed and deterministic.
    Crater centers are defined relative to the moon's bounding box,
    measured from the top-left corner of the moon body.

    At scale 1, the crater center positions are located at:
        - 1/5 from the left,  1/4 from the top
        - 3/7 from the left,  5/8 from the top
        - 1/4 from the left,  7/9 from the top
        - 4/5 from the left,  2/7 from the top
        - 7/12 from the left, 1/5 from the top
        - 2/3 from the left,  2/5 from the top
        - 5/8 from the left,  3/4 from the top
        - 7/20 from the left, 3/7 from the top
        - 3/20 from the left, 5/9 from the top
        - 3/4 from the left,  3/5 from the top

    At scale 1, crater radii are:
        3, 5, 4, 2, 6, 3, 4, 2, 5, 3 pixels

    Rendered crater radius:
        base crater radius * S

    Crescent moon rendering is a stretch goal and is not required for the
    initial Moon macro.


E: DoubleBox
------------
    ICEXXYYxxyyPP

    XX,YY = first corner
    xx,yy = opposite corner
    PP    = percentage split position from the top, stored as two-character base-36

    Draws an outlined rectangle, then draws a horizontal divider line across
    the rectangle.

    The divider is placed PP percent down from the top edge of the rectangle,
    splitting the rectangle into a top box and a bottom box.

    PP is clamped to the range 0-100 decimal.


GUI
=====================

Constructor Program:
--------------------
    The Constructor GUI is a packet-first visual editor for creating EMEIMG
    instruction files.

    The GUI does not store arbitrary drawing objects as the primary source of
    truth. Instead, each completed layer is stored as an EMEIMG packet string.
    The preview canvas is reconstructed by parsing and rendering the same
    packet strings that will later be saved and transmitted.

    This ensures that any image created in the Constructor is already valid
    according to the packet reconstruction protocol.

Canvas:
-------
    The GUI editing canvas represents the fixed EMEIMG image canvas:

        Width  = 720 pixels
        Height = 480 pixels

    Only the editable 720x480 region should be shown as the active drawing
    area. Any surrounding GUI space is not part of the reconstructed image.

Basic Workflow:
---------------
    The normal Constructor workflow is:

        1. Select a color.
        2. Select a shape.
        3. Click the canvas to define the shape origin.
        4. If required by the shape, click a second point.
        5. Adjust shape-specific fields if needed.
        6. Click "Add Command" to save the packet as a layer.

    Each saved layer corresponds to one packet line.

    The Constructor automatically assigns the packet instruction index I
    based on the current layer/order position.

    Example:
        First saved command  -> I = 0
        Second saved command -> I = 1
        Third saved command  -> I = 2

    The instruction index ranges from 0 to Z, giving a maximum of 36 ordered
    packet instructions.

Layer / Packet List:
--------------------
    The GUI maintains a list of saved packet commands.

    Each list entry represents one EMEIMG drawing instruction.

    The main preview renders all commands up to the current selected layer.
    This allows the user to preview the image build-up step by step.

    The final image preview renders all saved commands in instruction order.

    Deleting or reordering layers should renumber packet instruction indexes
    so that the first command is 0, the second command is 1, and so on.

Critical Element / Priority Metadata:
-------------------------------------
    The Constructor GUI includes a "Critical Element" checkbox.

    When checked, the saved command line receives a metadata tag appended to
    the end of the packet line:

        [PRIORITY]

    The priority tag is not part of the 13-character EMEIMG packet.

    The priority tag is transmission metadata used by the later feeder program
    that reads Constructor output and feeds commands into WSJT-X.

    The purpose of the tag is to identify elements that should receive extra
    transmission redundancy.

    A priority-tagged command line has this structure:

        <13-character EMEIMG packet>[PRIORITY]

    There is no separator character between the packet and the metadata tag.

    Example using a text packet:

        0300A0FKE9ETA[PRIORITY]

    In that example:

        0       = instruction index
        3       = color code
        0       = text shape
        0A0F    = text origin coordinate
        KE9ETA  = six-character text payload
        [PRIORITY] = metadata tag, not packet data

    The Constructor preview and image reconstructor must ignore the priority
    tag when rendering.

    The packet parser should strip or separate [PRIORITY] before interpreting
    the 13-character packet.

    The priority flag should be preserved when saving, loading, editing, or
    renumbering command layers.

Priority Transmission Behavior:
-------------------------------
    The [PRIORITY] tag is intended for the transmission feeder program, not
    the image renderer.

    The feeder program may use [PRIORITY] to send important packets more times
    than non-priority packets.

    This allows limited JT65B send cycles to be spent more intelligently.

    Important structural or identifying elements can receive additional
    redundancy, while minor cosmetic elements can be transmitted fewer times.

    Examples of elements that may be marked [PRIORITY]:

        - Callsign text
        - Main subject outline
        - Required identifying symbols
        - Critical geometry needed for image recognition
        - Important Moon / antenna / radio elements
        - Any element that would significantly damage the meaning of the image
          if lost

    Examples of elements that may be left non-priority:

        - Decorative stars
        - Cosmetic background details
        - Optional accent lines
        - Minor visual embellishments

    Priority does not change render order.

    Priority does not change packet geometry.

    Priority does not change the 13-character packet contents.

    Priority only informs the later transmission scheduler that the element
    should receive additional redundancy.

File Format Notes:
------------------
    Constructor output should be saved as one command per line.

    A command line may be either:

        <13-character EMEIMG packet>

    or:

        <13-character EMEIMG packet>[PRIORITY]

    The [PRIORITY] tag must appear after the complete 13-character packet.

    If a packet contains trailing spaces as unused wildcard/padding values,
    those spaces are still part of the 13-character packet. The [PRIORITY]
    tag begins after the 13th packet character.

    File readers should remove newline characters only.

    Do not strip trailing packet spaces before packet parsing.

    Recommended loading process:

        1. Read one line.
        2. Remove newline characters only.
        3. Check whether the line ends with [PRIORITY].
        4. If present, remove [PRIORITY] and store priority=True.
        5. Parse the remaining 13-character packet.
        6. Render the packet normally.
        7. Preserve priority metadata for later transmission scheduling.

Rendering Behavior:
-------------------
    The GUI preview renderer should ignore [PRIORITY].

    The standalone image reconstructor should also ignore [PRIORITY].

    Rendering should only use the 13-character EMEIMG packet.

    A priority-tagged packet and a non-priority packet with the same first
    13 characters should render identically.

    Example:

        0300A0FKE9ETA
        0300A0FKE9ETA[PRIORITY]

    Both render the same text element.

    The only difference is that the second command is marked for additional
    transmission redundancy by the feeder program.


Feeder

=====================

    The Feeder GUI is responsible for taking a completed Constructor output
    file and scheduling it for transmission.

    The Feeder does not generate image geometry.

    The Feeder reads saved EMEIMG packet lines, identifies metadata such as
    [PRIORITY], determines transmission order, applies redundancy rules, and
    outputs packets to the transmit path.

    In the prototype version, the transmit path is represented by console
    output.

    In a future version, this console output may be replaced with or connected
    to a WSJT-X, MAP65, or other JT65B-capable transmit-control interface.

GUI Fields:
-----------
    The Feeder GUI contains the following user-editable fields:

        Callsign:
            The transmitting station callsign.

            Example:
                KE9ETA

        EMEIMG Version Number:
            The protocol/image format version number.

            Example:
                1

        Image Number:
            A two-character Base-36 image identifier.

            Valid range:
                00 through ZZ

            Examples:
                00
                01
                0A
                10
                ZZ

    The version number and image number are combined into the automatic
    version header packet:

        EMEIMGV[version][image number]

    Example:
        EMEIMGV100

GUI Buttons:
------------
    Open File:
        Opens a text-based .emeimg file created by the Constructor program.

        The file should contain one EMEIMG packet line per instruction.

    Transmit:
        Begins transmitting the loaded file according to Feeder scheduling
        rules.

        In the prototype, each transmission is printed to the console.

    Pause Transmit:
        Temporarily pauses the active transmission queue.

        Pausing does not erase the queue and does not reset the current
        transmission position.

        Resuming continues with the next unsent transmission.

    Stop Transmit:
        Stops the active transmission and resets the current transmit position.

        A stopped transmission must be restarted from the beginning.

Input File Handling:
--------------------
    The Feeder reads Constructor output as one command per line.

    Each command line may be either:

        <13-character EMEIMG packet>

    or:

        <13-character EMEIMG packet>[PRIORITY]

    The [PRIORITY] tag is metadata only.

    The [PRIORITY] tag is not transmitted as part of the EMEIMG packet.

    The Feeder should remove newline characters from each file line, but should
    not strip trailing packet spaces before parsing the 13-character packet.

    This is important because Shape 0 text packets may use spaces as literal
    text payload characters.

    Recommended Feeder loading process:

        1. Read one line from the .emeimg file.
        2. Remove newline characters only.
        3. Check whether the line ends with [PRIORITY].
        4. If [PRIORITY] is present, store priority=True.
        5. Remove the [PRIORITY] metadata tag.
        6. Preserve the remaining 13-character packet exactly.
        7. Add the packet to the transmission queue.

Priority Metadata:
------------------
    The [PRIORITY] tag tells the Feeder that a packet should receive additional
    transmit redundancy.

    Priority does not change the packet contents.

    Priority does not change the packet's render order.

    Priority does not change the packet's geometry, color, or shape behavior.

    Priority only changes how the Feeder schedules transmission.

    A priority packet is transmitted three times.

    Example file line:

        IC2000014140*[PRIORITY]

    Actual transmitted packet:

        IC2000014140*

Priority Repeat Count:
----------------------
    Priority packets are sent:

        3 times

    Non-priority packets are sent:

        1 time

    This allows important image elements to receive extra redundancy without
    spending unnecessary transmit cycles on cosmetic details.

Automatic Feeder Packets:
-------------------------
    The Feeder automatically generates several transmission packets that are
    not stored as normal Constructor drawing instructions.

    These packets are used for station identification, image session
    identification, and transmission closure.

Opening Station ID Header:
--------------------------
    Before sending image data, the Feeder sends:

        [CALLSIGN] EMEIMG

    Example:

        KE9ETA EMEIMG

    This identifies the transmitting station and indicates that an EMEIMG
    transmission is beginning.

    The opening station ID header is treated as a priority packet.

    It is transmitted three times.

Version Header:
---------------
    After the opening station ID header, the Feeder sends the image version
    header:

        EMEIMGV[version][image number]

    Example:

        EMEIMGV100

    This packet identifies the EMEIMG version and the image number being
    transmitted.

    The version header is treated as a priority packet.

    It is transmitted three times.

Image Packet Scheduling:
------------------------
    After the automatic opening headers are sent, the Feeder schedules the
    packets loaded from the .emeimg file.

    Priority packets are sent before non-priority packets.

    Order is preserved within each priority group.

    Recommended scheduling process:

        1. Load all packet lines from the .emeimg file.
        2. Separate priority packets from non-priority packets.
        3. Preserve the original file order inside each group.
        4. Queue all priority packets first.
        5. Queue all non-priority packets after priority packets.
        6. Repeat each priority packet three times.
        7. Send each non-priority packet once.

    Example file order:

        Packet A
        Packet B[PRIORITY]
        Packet C
        Packet D[PRIORITY]

    Feeder scheduling order:

        Packet B
        Packet B
        Packet B
        Packet D
        Packet D
        Packet D
        Packet A
        Packet C

    This transmission ordering does not affect final render order because the
    reconstructor renders packets by their instruction index I, not by receive
    order.

Station ID During Transmission:
-------------------------------
    The Feeder periodically inserts the station ID during the transmission.

    Every 10th console transmission slot is reserved for:

        [CALLSIGN] EMEIMG

    Example:

        KE9ETA EMEIMG

    This provides repeated station identification during a long EMEIMG
    transmission.

    The inserted station ID is not an image drawing packet.

    It is transmit-session metadata and should not be parsed as an EMEIMG
    drawing instruction by the image reconstructor.

    Example transmission spacing:

        0001: KE9ETA EMEIMG
        0002: KE9ETA EMEIMG
        0003: KE9ETA EMEIMG
        0004: EMEIMGV100
        0005: EMEIMGV100
        0006: EMEIMGV100
        0007: priority image packet
        0008: priority image packet
        0009: priority image packet
        0010: KE9ETA EMEIMG
        0011: next image packet

Final Closing Packet:
---------------------
    After all image packets have been transmitted, the Feeder sends a closing
    packet:

        [CALLSIGN] 73

    Example:

        KE9ETA 73

    The closing packet indicates that the EMEIMG transmission is complete.

    The closing packet is treated as a priority packet.

    It is transmitted three times.

Overall Transmission Order:
---------------------------
    The complete Feeder transmission sequence is:

        1. Send [CALLSIGN] EMEIMG three times.
        2. Send EMEIMGV[version][image number] three times.
        3. Sort loaded file packets with priority packets first.
        4. Send priority image packets three times each.
        5. Send non-priority image packets once each.
        6. Insert [CALLSIGN] EMEIMG into every 10th transmission slot.
        7. Send [CALLSIGN] 73 three times after all image packets are complete.

Example:
--------
    Callsign:
        KE9ETA

    Version:
        1

    Image Number:
        00

    Automatic opening priority transmissions:

        KE9ETA EMEIMG
        KE9ETA EMEIMG
        KE9ETA EMEIMG
        EMEIMGV100
        EMEIMGV100
        EMEIMGV100

    Automatic closing priority transmissions:

        KE9ETA 73
        KE9ETA 73
        KE9ETA 73

Console Output:
---------------
    In the prototype Feeder, transmissions are printed to the console.

    Console output is a stand-in for a future transmit interface.

    The console should show:

        - Transmission number
        - Transmitted text
        - Transmission type/source

    Example:

        0001: KE9ETA EMEIMG    [priority-header]
        0002: KE9ETA EMEIMG    [priority-header]
        0003: KE9ETA EMEIMG    [priority-header]
        0004: EMEIMGV100       [priority-version-header]
        0005: EMEIMGV100       [priority-version-header]
        0006: EMEIMGV100       [priority-version-header]
        0007: IC2000014140*    [priority-packet]

Transmit Timing:
----------------
    The prototype Feeder may use a shortened delay between console outputs for
    testing.

    In real JT65B operation, the timing would need to respect the JT65B
    transmission cycle and whatever timing/API constraints are required by
    WSJT-X, MAP65, or the chosen transmit interface.

Pause / Resume Behavior:
------------------------
    When paused, the Feeder should stop advancing through the transmission
    queue.

    The current queue should remain intact.

    When resumed, the Feeder should continue from the next unsent item.

    Pause should not rebuild or reorder the queue.

Stop Behavior:
--------------
    When stopped, the Feeder should cancel the active transmission queue and
    reset the transmit position.

    Restarting transmission after a stop should rebuild the queue from the
    currently loaded file and current GUI field values.

Error Handling:
---------------
    The Feeder should not crash if a file contains malformed lines.

    Recommended behavior:

        bad line -> report warning -> skip line or mark invalid -> continue

    Lines that are blank should be ignored.

    Lines beginning with comment markers may be ignored.

    Suggested comment markers:

        #
        //

    If a packet is not exactly 13 characters after removing [PRIORITY], the
    Feeder should report it as malformed.

    If a malformed packet is skipped, the console should identify the source
    line number when possible.

Important Separation of Roles:
------------------------------
    Constructor:
        Creates packet lines and optionally appends [PRIORITY].

    Feeder:
        Reads packet lines, schedules transmissions, repeats priority items,
        inserts station ID, and sends output to the transmit path.

    Reconstructor:
        Ignores [PRIORITY] and reconstructs the image from valid 13-character
        EMEIMG packets.

    The Feeder is part of the transmission system, not the image renderer.



Implementation Notes:
=====================

    Invalid packets should not crash the reconstructor.

    If a packet is malformed, the parser should report the issue in the
    terminal and convert the packet into a VOID/no-op instruction.

    Recommended invalid-packet behavior:
        bad packet -> print warning -> return VOID -> continue rendering

    Packet parsing should preserve literal spaces in Shape 0 text packets.
    When reading packets from a file, remove newline characters only.
